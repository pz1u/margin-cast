# Decision Engine 데이터 출처와 판단 방법

## 현재 데이터 출처

현재 MarginCast Decision Engine은 실제 매장 POS가 아니라 재현 가능한
`synthetic-pos-v2` 데이터로 검증하는 프로토타입이다. 수요 기준선과 가격탄력성은 합성 데이터의
관측 가능한 주문·가격·할인·원가·날씨 필드만 사용해 학습한다. 숨겨진 생성 파라미터인
`ground_truth.json`은 학습이나 시뮬레이션에 사용하지 않고 추정 결과를 평가할 때만 사용한다.

API와 Agent 도구 결과의 `data_provenance`는 다음 사실을 항상 노출한다.

- `source_type`: `synthetic_pos`
- `dataset_version`: `synthetic-pos-v2`
- `uses_actual_store_data`: `false`
- 학습 기간과 학습 행 수
- 실제 매장 성과를 보증하지 않는다는 경고

실제 POS 연결 전 결과는 사업 조언의 확정값이 아니라 계산 흐름과 실험 설계를 검증하는
프로토타입 결과로 해석해야 한다.

## 수요·효과·불확실성

- 수요 기준선은 가격·할인·요일·시간·채널·날씨 등 관측 문맥으로 추정한다.
- 가격탄력성과 할인 노출 효과는 학습 기간의 반복 실험으로 분리해 추정한다.
- Monte Carlo는 수요 변동, 탄력성·할인 효과의 추정오차와 원가 변동을 반영한다.
- 성공확률은 같은 미래 문맥에서 전략 이익이 기준 이익보다 클 모의실험 비율이다.
- 80% 예상 범위는 기여이익 변화 분포의 10~90 백분위다.

## 근거 품질 `heuristic-v1`

`evidence_quality`는 성공확률이나 통계적 신뢰수준이 아니다. 현재 버전은 다음 네 항목을 합산한
0~100점 휴리스틱이다.

| 구성 요소 | 최대 점수 | 의미 |
|---|---:|---|
| 실험 근거 | 30 | 반복 가격·할인 실험과 관측 가격 수준 |
| 추정 정밀도 | 30 | 효과 추정치 대비 강건 표준오차 |
| 시나리오 지지 | 20 | 제안 실결제가가 관측 범위 안에 있는 정도 |
| 날씨 문맥 | 20 | 실제 미래 단기예보 사용 여부. 관측 이력 재사용은 5점 |

- `HIGH`: 80점 이상
- `MEDIUM`: 50점 이상 80점 미만
- `LOW`: 50점 미만

현재 `validation.status`는 `PENDING_REAL_STORE_FEEDBACK`이다. 실제 매장 피드백이 없으므로
점수가 높은 예측이 실제로 더 정확한지는 아직 검증되지 않았다. 이 상태를 API와 웹에서 함께
표시하며, 검증 전에는 점수를 과학적으로 보정된 신뢰도로 표현하지 않는다.

응답에는 `formula_fingerprint`도 포함한다. 산식에 쓰는 가중치·임계값을 정규화한 SHA-256
지문이며, `heuristic-v1`에 등록된 기준 지문과 다르면 모듈 로딩과 테스트가 실패한다. 따라서
가중치나 임계값을 바꿀 때는 새 버전과 기준 지문을 함께 등록해야 한다. 소스 파일 전체 해시를
사용하지 않아 주석·포맷 변경은 새 산식으로 오인하지 않는다.

이 검증은 테스트 전용이 아니다. `src.evidence_quality`가 import될 때 실행되므로 지문이 맞지
않는 배포본은 HTTP 서버 모듈 로딩 단계에서 실패하고 요청을 받는 상태까지 올라오지 않는다.
이미 실행 중인 Python 프로세스의 파일을 디스크에서만 바꿔도 메모리의 정책은 바뀌지 않으며,
다음 배포·재시작에서 검증된다. 정상 기동한 서버의 `/api/health`는 현재 로딩된 버전과 지문을
노출해 배포 결과를 확인할 수 있게 한다.

정책은 `MappingProxyType`으로 노출해 실행 중 일반적인 값 변경도 막는다. 이 장치는 등록된
가중치·임계값 변경을 감지하며, 임의의 계산 코드 변경 전체를 해시하는 장치는 아니다. 계산
흐름의 회귀는 별도의 행동 테스트로 검증한다.

## 실행 판단

Decision Engine은 기대 기여이익, 개선확률, 80% 범위 하한과 근거 품질을 함께 사용한다.

- `HOLD`: 기대이익이 양수가 아니거나 개선확률이 50% 미만
- `EXPERIMENT`: 기대 개선은 있지만 근거 품질이 `LOW`, 80% 하한이 음수 또는 개선확률이 75% 미만
- `RECOMMEND`: 개선확률 75% 이상, 80% 하한 0 이상, 근거 품질 `MEDIUM` 이상

근거가 부족할 때 `EXPERIMENT`는 실패 응답이 아니다. 적용 범위를 제한하고 실제 결과를
수집하기 위한 다음 행동이다. 가격 변화가 한 수준만 관측된 메뉴는 탄력성을 추측하지 않고,
기준 가격 외 최소 한 개 가격을 별도 기간에 운영하라는 데이터 확보 경로를 반환한다.

## 날씨 해석 경계

기상청 예보는 미래 날짜의 온도·강수·습도 문맥을 수요 기준선에 넣는 용도다. 예보를 사용했다는
사실만으로 특정 메뉴에서 비가 수요를 증가시킨다는 인과관계를 입증하지 않는다. 응답의
`weather_context.menu_specific_causal_effect_validated`는 현재 항상 `false`다.

Agent 평가에는 날씨가 포함됐지만 메뉴별 날씨 민감도가 검증되지 않은 질문을 넣고, 에이전트가
인과효과를 확정적으로 설명하지 않는지 회귀 테스트해야 한다.

## 실제 피드백을 이용한 검증

실험 계획에는 당시 Decision Engine 버전, 데이터 출처, 날씨 문맥, 근거 품질 버전·정책
지문·점수·등급과 실행 판단을 예측 분포와 함께 저장한다. 실제 결과가 연결되면 근거 품질
버전·등급별로 다음을 집계한다.

- 기여이익 변화 평균 절대 오차
- 80% 예측 구간 포함률
- 이익 개선 방향 정확도

충분한 실제 실험이 쌓이기 전에는 등급과 정확도의 관계를 결론 내리지 않는다. 산식이나 가중치를
바꾸면 새 버전을 발급하고, 과거 기록은 당시 버전을 유지한다.

## 근거 품질 버전 호환 규칙

`heuristic-v2`를 추가해도 과거 v1 실험을 v2 점수로 덮어쓰거나 다시 등급화하지 않는다. 실험
계획에는 당시 `score`, `label`, `version`, `formula_fingerprint`가 함께 남으므로 “당시 v1 기준
MEDIUM” 상태는 v2 도입 뒤에도 그대로 조회한다. 보정 집계는 다음 세 값을 그룹 키로 사용한다.

```text
(version, formula_fingerprint, label)
```

따라서 v1 `MEDIUM`과 v2 `MEDIUM`을 같은 표본으로 합치지 않는다. 새 버전을 구현할 때는 과거
정책 정의와 평가기를 제거하지 않고 버전별 레지스트리에 보존해야 과거 입력을 다시 계산할 수
있다. 현재 저장 구조는 당시 결과 조회와 버전별 집계를 지원하지만, 지문만으로 과거 산식을
복원할 수는 없다. v2 구현 전 버전별 정책·평가기 레지스트리를 추가하는 것이 필수 조건이다.
